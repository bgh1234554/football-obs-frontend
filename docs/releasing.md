# 릴리즈 절차

football-obs-frontend의 새 버전을 출시할 때 따르는 절차입니다. 처음 릴리즈를 진행하는 사람도 순서대로 따라 할 수 있게 썼습니다.

이 문서의 버전 번호 기준과 출시 절차는 **관리 방안 제안**입니다. 프로젝트 정책으로 확정되면 이 문장을 지우고 확정된 내용으로 고쳐 주세요.

## 문서별 역할

| 문서 | 독자 | 내용 |
| --- | --- | --- |
| [README.md](../README.md) | GitHub 저장소를 처음 방문한 사람 | 프로젝트 소개, 빠른 시작, OBS 사용법, 링크 |
| [about.md](../about.md) | 대시보드 사용자 | 탭별 기능, 설정, 단축키. 앱의 About 탭에 그대로 표시됨 |
| [CHANGELOG.md](../CHANGELOG.md) | 업데이트 내용을 확인하려는 사용자 | 버전별 변경 내용 |
| GitHub Release | 출시 소식을 보는 사용자 | 한 버전의 출시 안내. CHANGELOG의 해당 버전을 바탕으로 작성 |

기능을 바꾸면 about.md의 설명도 같이 고칩니다. README에는 변경 이력을 쓰지 않습니다.

## 용어

- **안정 브랜치**: 출시할 코드가 모이는 브랜치입니다.
- **태그**: 특정 커밋에 붙이는 이름표입니다. `v1.0.0` 태그는 1.0.0 버전을 출시한 순간의 코드를 가리키며, 이후 브랜치에 커밋이 쌓여도 태그가 가리키는 커밋은 바뀌지 않습니다.
- **GitHub Release**: 태그에 연결된 출시 안내 페이지입니다. 저장소의 Releases 메뉴에 표시되고, 그 시점의 소스 코드 압축 파일이 자동으로 첨부됩니다.

관계를 정리하면 다음과 같습니다.

```text
출시 커밋  <-  태그 v1.0.0  <-  GitHub Release "v1.0.0" (출시 안내)
```

## 브랜치와 배포 구조

| 브랜치 | 역할 |
| --- | --- |
| `feature/*` | 작업 브랜치. Pull Request로 `develop`에 병합 |
| `develop` | 다음 출시에 들어갈 작업이 모이는 브랜치 |
| `master` | **안정 브랜치.** 출시한 코드만 들어가며, 태그와 GitHub Release도 이 브랜치의 커밋에 붙임. GitHub 기본 브랜치 |

정식 출시 후에는 Vercel이 `master`에 병합된 코드를 운영 사이트에 배포합니다.

### 베타 기간의 임시 구조 (2026-10-08 기준)

지금은 베타 운영 중이라 Vercel 운영(Production) 배포가 `develop` 병합 때마다 실행되고, `master`는 2026-04-06 이후 갱신되지 않았습니다. 최초 정식 릴리즈 전에 다음을 한 번 해야 합니다.

1. Vercel 대시보드 **Settings > Git > Production Branch**를 `master`로 바꿉니다.
2. 아래 출시 절차대로 `develop`을 `master`에 병합합니다. 현재 `master`에는 `develop`에 없는 커밋이 없으므로 충돌 없이 병합됩니다.

이 작업이 끝나면 이 절을 지워 주세요. 그 전까지 README는 GitHub 저장소 첫 화면(`master`)에 표시되지 않습니다.

## 버전 번호 정하기

`MAJOR.MINOR.PATCH` 형식(유의적 버전)을 제안합니다. 태그에는 앞에 `v`를 붙입니다(`v1.2.3`).

| 올리는 자리 | 언제 | 예시 |
| --- | --- | --- |
| PATCH (`1.0.0` -> `1.0.1`) | 버그 수정만 있을 때 | 이벤트 시간이 잘못 표시되던 문제 수정 |
| MINOR (`1.0.1` -> `1.1.0`) | 기존 사용법을 유지하면서 기능을 추가할 때 | 새 패널, 새 설정 항목 추가 |
| MAJOR (`1.1.0` -> `2.0.0`) | 기존 사용 방식과 호환되지 않게 바뀔 때 | 저장된 설정이 초기화됨, 단축키 체계 변경, 화면 구성을 크게 바꿔 OBS 장면을 다시 맞춰야 함 |

이 프로젝트는 설치형 프로그램이 아니라 웹사이트라서 사용자는 항상 최신 배포본을 씁니다. 그래서 MAJOR는 "사용자가 무언가를 다시 설정해야 하는가"를 기준으로 판단하는 것을 권장합니다. 한 번에 여러 종류의 변경이 있으면 가장 큰 자리를 올립니다.

## 평소: 변경 내용 기록하기

사용자가 체감하는 변경이 있는 Pull Request는 CHANGELOG의 `## 미출시` 아래에 한 줄씩 추가합니다.

| 분류 | 쓰는 경우 |
| --- | --- |
| 추가 | 새 기능 |
| 개선 | 기존 기능을 더 낫게 바꿈 |
| 수정 | 버그 수정 |
| 변경·제거 | 동작이 바뀌거나 기능이 없어짐 |
| 업데이트 주의사항 | 사용자가 직접 해야 할 일(설정 다시 맞추기 등) |

- 커밋마다 쓰지 않습니다. 사용자 입장에서 의미 있는 변화만 씁니다.
- 내부 리팩토링, 테스트, 문서 오타 수정은 쓰지 않습니다.
- "무엇이 어떻게 바뀌었는지"를 사용자 언어로 씁니다. 예: "교체 선수가 라인업에 반영되지 않던 문제 수정"

## 출시 절차

`master`에 병합하는 순간 운영 사이트에 배포되므로, 버전 확정은 **병합 전에** 끝내야 합니다. 그래야 태그가 붙는 커밋과 운영 사이트의 코드가 같아집니다.

```text
feature/* --PR--> develop --출시 PR--> master --> Vercel 운영 배포
                                         |
                                         +--> 태그 v1.1.0 --> GitHub Release
```

### 1. 출시 준비 확인

- [ ] 출시할 기능이 모두 `develop`에 병합되어 있다.
- [ ] 테스트를 통과한다: `npm test --prefix tests` (설치 방법은 [tests/README.md](../tests/README.md))
- [ ] `develop`의 미리보기 배포(Vercel Preview)에서 경기 하나를 불러와 메인 화면 2종, 테마, 일정 확인, 전술판, About 탭을 확인했다.
- [ ] OBS에서 캡처해 점수판과 패널이 정상으로 보인다.
- [ ] 바뀐 기능이 about.md 설명과 일치한다.
- [ ] README의 링크와 이미지가 열린다.
- [ ] 백엔드 변경이 필요한 기능이라면 백엔드가 먼저 배포되어 있다.
- [ ] 커밋에 API 키 같은 비밀 값이 없다.

### 2. CHANGELOG에서 버전 확정

`develop`에서 `## 미출시` 제목을 버전과 출시 예정일로 바꾸고, 그 위에 빈 `## 미출시`를 새로 만듭니다. 작업 브랜치에서 고친 뒤 Pull Request로 `develop`에 넣어도 됩니다.

```markdown
## 미출시

## 1.1.0 - 2026-11-15
### 추가
- ...
```

날짜는 운영 사이트에 배포되는 날(= `master` 병합일)로 씁니다. 형식은 `YYYY-MM-DD`입니다.

### 3. 출시 Pull Request 만들기

`develop`에서 `master`로 Pull Request를 엽니다. 제목 예시: `release: v1.1.0`. 본문에는 CHANGELOG의 해당 버전 내용을 붙여 넣으면 검토하기 쉽습니다.

### 4. 병합하고 배포 확인

Pull Request를 병합하면 Vercel이 배포를 시작합니다. Vercel 대시보드나 Pull Request의 배포 상태에서 완료를 확인한 뒤 <https://football-obs-frontend.vercel.app>에서 새 기능이 보이는지 확인합니다.

### 5. 태그 붙이기

`master`의 병합 커밋(운영 사이트에 배포된 커밋)에 태그를 붙입니다. GitHub 웹 화면에서 Release를 만들면서 태그를 함께 만들 수 있으니 6단계로 바로 넘어가도 됩니다.

명령으로 하려면 다음과 같습니다(예시이며, 실제로 실행할 때 버전과 커밋을 확인하세요).

```bash
git switch master
git pull
git log -1 --oneline        # 배포된 병합 커밋인지 확인
git tag -a v1.1.0 -m "v1.1.0"
git push origin v1.1.0
```

- `-a`는 작성자와 날짜가 기록되는 태그를 만듭니다.
- 이미 푸시한 태그는 옮기지 않습니다. 잘못 붙였으면 다음 PATCH 버전으로 다시 출시하는 편이 안전합니다.

### 6. GitHub Release 작성

1. 저장소 페이지 오른쪽의 **Releases**를 누르고 **Draft a new release**를 누릅니다.
2. **Choose a tag**에서 5단계에서 푸시한 태그를 고릅니다. 태그를 아직 만들지 않았다면 새 태그 이름(`v1.1.0`)을 입력하고 **Target**을 `master`로 지정합니다.
3. **Release title**에 `v1.1.0`을 입력합니다.
4. 본문에 아래 템플릿을 붙여 넣고 CHANGELOG의 해당 버전 내용을 옮깁니다.
5. **Set as the latest release**가 선택되어 있는지 확인하고 **Publish release**를 누릅니다. 바로 공개하지 않으려면 **Save draft**로 저장해 둘 수 있습니다.

### 급한 버그 수정

운영 중 급히 고쳐야 할 버그는 `master`에서 작업 브랜치를 만들어 고친 뒤 `master`로 Pull Request를 엽니다. CHANGELOG에 PATCH 버전(예: `1.1.1`)으로 기록하고 위 4~6단계를 따릅니다. 출시 후 `master`를 `develop`에도 병합해 두 브랜치가 어긋나지 않게 합니다.

## 배포와 Release의 차이

| | 웹사이트 배포 | GitHub Release |
| --- | --- | --- |
| 하는 일 | 사용자가 쓰는 사이트를 새 코드로 바꿈 | 어떤 코드가 어떤 버전인지 기록하고 안내함 |
| 일어나는 시점 | `master`에 병합할 때 Vercel이 자동 실행 | 사람이 직접 작성할 때 |
| 서로의 영향 | Release를 만들지 않아도 배포됨 | Release를 만들어도 배포되지 않음 |

`master`에 병합하면 Release를 만들지 않아도 운영 사이트에 반영됩니다. 그래서 `master` 병합은 출시할 때만 하고, 병합할 때마다 태그와 Release를 함께 남기는 것을 권장합니다.
